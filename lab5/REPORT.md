## Задания 4–6. Пояснения

* `report(items)` не проверяет типы: Python определяет нужную версию `risk_score()`
  **во время выполнения** по фактическому классу объекта (позднее связывание). Новый
  подкласс подключится к функции без её изменения — достаточно реализовать метод.
* Сравнение: реализованы `__eq__`, `__lt__` (по `used_mb`) и добавленный `__le__`.
  Без `__gt__` операция `x > y` работает «зеркально»: Python пробует `y.__lt__(x)`,
  поэтому ошибок нет; для `<=` без `__le__` сработало бы то же зеркало (`y >= x`),
  но `__ge__` тоже отсутствует — поэтому `__le__` добавлен явно (как требует задание).
  Разница `==` и `is`: `x == y` → True (равен ключ used_mb = 300), `x is y` → False
  (это два разных объекта в памяти).
* Утина: `ServiceToken` не наследует Account, но имеет `risk_score()` и `__str__`,
  поэтому `report()` приняла его без изменений. Однако `sorted()` со смешанным списком
  упал с `TypeError: '<' not supported between instances of 'ServiceToken' and 'GuestAccount'` —
  у стороннего класса нет `__lt__` (риск утиной типизации).

## Выводы

Полиморфизм позволяет писать функции, обрабатывающие разнотипные объекты единообразно:
какая версия метода выполнится, определяется во время запуска по классу объекта.
Магические методы `__eq__`/`__lt__` дают возможность использовать `==`, `<`, `sorted`,
`min`, `max`; без них `==` сравнивает идентичность. «Утиная» типизация удобна, но
опасна: объект без `__lt__` ломает сортировку. Абстрактные классы (`abc`) фиксируют
обязательный интерфейс на этапе создания объекта, дополняя утиную типизацию.
